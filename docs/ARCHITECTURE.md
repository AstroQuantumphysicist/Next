# Architecture and implementation boundaries

The [Next 1.0 specification](NEXT-1.0-SPEC.md) defines the target product; it is document content, not agent instructions or an implementation report. The [requirement inventory](requirements.json) and [generated status](STATUS.md) track acceptance gates. Current functionality is an independently booted development system with bounded native execution and device profiles. It does not satisfy the full specification.

## Boot and ownership

NextBoot is a Rust UEFI application for `x86_64-unknown-uefi`. Firmware loads `EFI/BOOT/BOOTX64.EFI`; NextBoot verifies `EFI/NEXT/SYSTEM.NXP`, then reads `EFI/NEXT/HELIX.ELF` and `EFI/NEXT/INITRD.NXI` from that loaded image's own boot-device filesystem. The kernel profile accepts fixed-address, page-aligned x86-64 ET_EXEC PT_LOAD segments at 64 MiB. It rejects architecture mismatches, malformed bounds, overlap, bad entry points, W+X and unsupported dynamic records before execution. Allocation covers the entire kernel span; copying zeroes BSS and gaps.

The init image is a bounded contiguous NEXTINIT v1 archive with up to 64 entries, 80-byte entries and a 16 MiB total limit, canonical absolute names, checked offsets, a fixed format version and CRC32. The boot path requires `/system/nextd.elf`. Its archive format does not carry a signature; NextBoot separately compares its complete SHA256 digest against the verified signed deployment. CRC supplies additional corruption detection and does not grant authority. Boot retains the archive allocation for the kernel and releases temporary file handles/buffers before acquiring the final memory-map key.

After `ExitBootServices`, NextBoot seals the retained 168-byte BootInfo development ABI 0.2 and jumps to the separate ELF through SysV64. Helix switches to a guarded stack, validates checksums/version/ranges and the firmware map, and requires kernel, loader/BootInfo, init image and map storage to be covered by loader-owned descriptors without retained-range overlap. Only conventional memory feeds the physical-page allocator. The kernel uses `x86_64-unknown-none`, a custom linker script, no host runtime/interpreter and a disabled red zone. Kernel placement is fixed, not randomized; loader allocations are retained rather than generally reclaimed.

The next source-stage AP foundation requests exactly one 4 KiB `EfiLoaderData` page at physical `0x80000` using UEFI `AllocateAddress`. Failure leaves the BSP path operational. The retained BootInfo `AP_TRAMPOLINE_RESERVED` flag is included in its checksum; its 168-byte layout and version are unchanged, and unknown flag bits are rejected. The kernel may authorize this page only after validating the flag, complete non-runtime LoaderData coverage in the retained final map, and absence of overlap with kernel, loader, init image, map-storage pages or framebuffer. A coalesced LoaderData descriptor is permitted; unrelated low LoaderData without the explicit flag grants no reservation. Failed handoffs release the page and private map allocation while boot services remain live; successful exit retains both without subsequent firmware calls. This source-stage foundation has host checks and is not guest AP-startup evidence.

The reserved page remains supervisor-only and non-executable under the current low-memory mapping. An uninvoked mapping prerequisite accepts only a validated reservation and at most 4 KiB of image bytes contained in the authenticated kernel’s linker-bounded read-only image. Its pure policy rejects changed huge-page permissions, unknown cache flags, wrong physical leaves, empty/oversized images and source-range overflow. Its hardware path requires IF clear, the owned kernel root, write protection and NX; it initializes the reserved page while still RW/NX, splits the first 2 MiB using a permanently retained supervisor page table, then publishes exactly one RO/RX leaf. All other low pages stay RW/NX, shared process roots retain supervisor denial, and global/cached translations are flushed. Read-only source containment proves storage ownership; correctness of the startup image remains a trusted caller obligation. Host policy tests cover every resulting leaf, but the hardware mapping API has not been called or guest-validated.

Activation remains blocked on a complete reviewed startup image, separate RW/NX bootstrap mailboxes, isolated AP stack/GDT state, safe INIT/SIPI timeout/acknowledgment handling and failure containment. No INIT/SIPI, AP execution, SMP scheduling or shared interrupt/runtime state is enabled by this reservation. Existing global TSS, interrupt stacks and process context ownership remain BSP-only.

The following source stage contains an unactivated 16/32/64-bit park image and private bootstrap state for at most 16 APs. Each retained slot has a 64 KiB RW/NX stack between two unmapped guard pages, a private IDT, an enabled MADT/xAPIC identity, and a unique nonzero request token. The immutable image supplies its own bootstrap GDT, checks CPUID identity/features, acquires its slot, loads the owned BSP page-table root, checks a validated HPET counter against its request deadline, publishes its token, and uses a compare-exchange to acknowledge readiness before parking with IF clear. It calls no Rust function, installs no global TSS/IST, and never touches the native scheduler or process-context globals. BSP timeout permanently quarantines its slot; late acknowledgment cannot change quarantine back to ready, and its resources are never reassigned. The preparation API refuses operation while trampoline mapping is inactive and requires exact mapped image bytes, the owned root, actual private-stack guard leaves and the caller's validated HPET resource. It contains no INIT/SIPI sender and remains uncalled.

An isolated unsigned audit ELF retains otherwise unused image bytes with explicit `-C link-dead-code=yes`; that linkage is a host audit artifact, not a boot deployment. The mixed-mode byte/disassembly audit verifies far-offset width/targets, GDT encoding, immutable source-load permissions, bounded ownership CAS and disabled-interrupt park loops. Five compiled-byte mutation cases reject a missing real-mode 32-bit far-offset prefix, changed GDT, writable source segment, interrupt-enabled entry and unlocked ready CAS. These checks establish encoding and policy only. Before its private long-mode IDT is installed, the prototype deliberately uses a null transition IDT; an early NMI could shut down that AP. NMI-source quiescence or safe transition handling, complete activation protocol review and guest AP execution/timeout proofs remain blockers. No AP has been started by this source stage.

The NMI transition review explicitly blocks `prepare` with `NmiTransition`, even if a future caller activates the reservation mapping. A phase model reports unsupported pre-entry quiescence, absence of an owned writable low stack at real entry, and the current null IDT through protected/paging transitions. Only the already-designed private long-mode stack/IDT is modeled as covered; no phase has guest execution evidence. There is no caller-supplied boolean that can bypass the activation blocker.

A candidate NMI-only dual-format table has disjoint vector2 records at offsets 8, 16 and 32 for real, protected and long mode. Independent architectural-format tests decode their handler addresses and selectors. This layout does not solve other exceptions: the protected vector2 record is interpreted as real vector4, which can target unrelated low memory. A separate candidate geometry check shows how sixteen disjoint 256-byte real-mode emergency stacks could fit in an additional owned low page; it allocates nothing and grants no ownership. The 4 KiB RO code reservation alone cannot supply these writable stacks. A future change must establish explicit additional UEFI ownership, safe first-instruction stack state, all-vector transition containment and verifiable NMI-source handling. CMOS NMI masking alone cannot establish this because LAPIC/chipset/IPI sources remain independent. Startup remains unsupported.

The next source-stage loader separately attempts an exact 8 KiB `EfiLoaderData` reservation at `0x81000`, only after the code-page allocation succeeds. Its named `AP_BOOTSTRAP_SCRATCH_RESERVED` flag requires the code flag and is checksummed; layout/version remain unchanged and unknown bits still fail closed. `BootInfo::ap_bootstrap_scratch` authorizes only complete non-runtime LoaderData coverage of both reservations, accepting adjacent/coalesced descriptors while rejecting gaps, type/runtime changes and every retained/framebuffer alias. Scratch failure retains BSP operation with no scratch authority; a wrong returned address is freed through its owned allocation, and final-map mismatch prevents `ExitBootServices` and releases the retained owners. Paired host cases cover full success, scratch failure, code failure without a scratch attempt, wrong scratch address and map mismatch. This is source/host foundation evidence; it has not started an AP. The first scratch page is intended for private real-mode emergency stacks, the second for low metadata. The unactivated startup preparation remains blocked on NMI transition handling.

## Development deployment authentication

`next-package` verifies bounded canonical bundles with SHA256 and strict Ed25519 verification from pinned `sha2`/`ed25519-dalek` dependencies. Signatures cover the complete header and file table, including every content digest; the verifier hashes every payload before returning a verified value. It rejects malformed metadata, unknown/revoked signers, disallowed permissions/kinds, noncanonical signatures/keys and changed payloads. Verified package metadata alone does not authorize installation or execution. Guest application loading now verifies each signed application envelope before allocating a PID or mutating process mappings, binds its package ID/signer/digest to the exact executable bytes, and records an immutable principal. Native and explicit compatibility launches receive separately bounded development grants; capability insertion and inheritance obey the principal ceiling. Renaming an archive member cannot change its authenticated identity. The tampered signed application fixture is rejected before process creation. This is immutable development trust at generation zero, with fixture-class preauthorization; no user consent UI, credential/session service, persisted revocation or production launch-token policy is installed.

The boot loader trusts a compiled workspace development public key and permits only deployment bundles requesting no permissions. It requires the expected two-file kernel/init-image artifact set, then validates and hashes the standalone boot-device files before allocation/execution. A structurally valid ELF or CRC-resealed init archive with changed bytes is still rejected when its digest differs from the signed deployment. Actual QEMU rejection cases exercise these bindings and malformed/forged bundles without using a private key. See the [bundle format](../crates/next-package/README.md).

The host build uses a generated persistent development key pair and emits `SYSTEM.NXP`. Private key material remains outside boot artifacts. The EFI loader itself is unsigned: firmware does not authenticate this trust anchor under UEFI Secure Boot. An allocation-free host trust module verifies bounded owner-signed key-rotation chains with consecutive generations, attenuated ceilings and retired-key rejection. Its caller must protect and durably commit generation/anchor/revocation state; the EFI loader does not consume these transitions. There is no TPM measurement, production root provisioning or rotation/revocation delivery, repository expiry, monotonic anti-rollback state, OS installer or authenticated A/B update manager. A valid signature proves the bounded bundle under the selected development anchor, not a complete secure boot/update chain.

The optional host package installer operates in an existing private host directory. It verifies complete bundles before mutation, stages immutable digest-named deployments, synchronizes files/directories, and activates install/update/uninstall through an atomic bounded registry replacement. It retains the prior digest for verified rollback and isolates each package's namespace. Real temporary-directory tests cover transactions, conflicts, corruption, revocation and selected failure boundaries. Ancestors must remain trusted; crash-stale locks/staging require owner recovery, and durability depends on the host filesystem/device. This is a build-host prototype, not a guest `packaged` service, Next COW installer, dependency solver, repository manager or runtime permission UI.

## Memory and native processes

The low 4 GiB identity mapping is supervisor-only RW/NX by default. Kernel text is RX, constant data RO/NX and mutable data RW/NX. CR0.WP and EFER.NXE enforce permissions. Kernel and privilege-entry/interrupt stacks each have 64 KiB usable space and unmapped guards, and double faults use an emergency IST. Exact registered boot probes verify CPU denials; unexpected kernel faults remain fatal.

The development runtime has four process slots. Each process owns page tables, at most 256 KiB of native image space, a guarded 64 KiB user stack, saved integer/x87/SSE state, and a generation-checked capability table. User code maps at `0x4000000000`. Executable/read-only physical aliases are protected against kernel writes. Process mappings are removed and slot state cleared before reuse. Anonymous map/unmap calls allocate zeroed pages from a bounded per-process arena and enforce W^X and kernel-alias permissions. This remains a static allocation strategy without demand paging, general VMOs, shared-memory mapping, COW virtual memory or an SMP VM manager.

Native ELF files require a unique exact Next development ABI 0.1 note, mapped within file-backed read-only data. The loader accepts the documented fixed ET_EXEC profile and rejects unsupported executable requirements. A 48-byte startup record passes PID and authorized startup handles. Native `int 0x80` dispatch implements bounded logging, handle close/attenuated duplication, process spawn/wait/kill, yield/sleep, clock access, channel creation/send/receive, anonymous map/unmap, file streams, event objects, bounded one-shot monotonic timer capabilities and supervisor readiness. The process wait call returns syscall status separately from a signed 64-bit exit result copied to validated user memory. Successful repeated/duplicated waits retain that result and do not close the process handle; failed copyout cannot consume it. Manual-reset and auto-reset events have generation-checked handles, signal/reset rights and nonblocking polling through the same wait call. Output validation occurs before consuming an auto-reset signal. An unsignaled event can return WouldBlock or park the process through ObjectWait flag 1 with an optional absolute monotonic deadline. Timeout preserves output; completion revalidates authority and copyout before consuming an auto-reset signal. Teardown clears pending waits. One-shot timers have immutable deadlines, latched expiry/cancellation, WAIT/SIGNAL authority, eight global objects and two live objects per creator; boot-CPU expiry scans and serialized wait/cancel observations preserve equal-deadline ordering. They do not provide periodic/rearm callbacks, UTC alarms, high-resolution clock guarantees or SMP synchronization. Event-only atomic wait-any is bounded to sixteen inputs; general wait-many and cancellation-token protocols remain absent. The [native development ABI](NATIVE-ABI.md) records current call numbers and bounds. Numeric IDs and structures are experimental; this is not the specification's frozen syscall schema or a general source/binary SDK.

User copy helpers validate overflow, mapped-page bounds and required permissions before copying. Log buffers and IPC frames are bounded. Parent launch authority and process wait/signal rights are checked in the caller's handle table. Stale generations cannot address a recycled capability or process slot. Child initialization failures roll back reserved runtime state. Supervisor identity is protected from console kill requests.

Channels have four bounded messages per direction and payloads up to 256 bytes. Framing/version/reserved fields, deadlines, ownership and READ/WRITE rights are checked. Endpoint references and generations support close/peer-close behavior. A supervisor can deliberately inherit an attenuated endpoint into a child; messages can move capability handles with attenuated rights, including file-stream references. Transferred/duplicated file handles share the stream offset. General revocation, blocking wake/cancel semantics and cross-core transfer races remain outstanding.

The PIT/PIC clock drives single-CPU process preemption. Interrupt and syscall transitions preserve integer and x87/MMX/SSE state using a 512-byte FXSAVE profile; non-yielding child tests retain all XMM registers and x87 sentinels across actual switches. The kernel explicitly disables OSXSAVE/AVX, user FSGSBASE, protection keys, CET and UINTR controls, resets latent PKRU, and clears FS/GS/KERNELGS bases. Readback checks enforce that advertised development context policy even when the VM CPU exposes optional features. Explicit native calls set/get a bounded FS base; Linux arch_prctl supports bounded FS/GS set/get. Entry captures per-process bases and every gate/yield/timer switch restores the selected process state. Inherited bases start at zero, and user FSGSBASE remains disabled. Original native/Linux fixtures test pointers, bounds and overlapping process ownership. Timer callbacks do not allocate or lock, and kernel references do not survive transitions into user mode. Validated ACPI discovery now reports BSP/processor entries, IOAPICs and interrupt overrides; it does not start APs or route interrupts. The d4f7b7da7ef8 VM milestone maps validated HPET MMIO through an owned uncached region and observes its hardware counter advancing. PIT remains the scheduler clock. Read-only BSP LAPIC identity/version and IOAPIC pin discovery use validated owned uncached mappings; an ISA routing plan is computed while redirection stays unchanged. The earlier f42210 milestone rejected HPET as PhysicalRange. A q35 CMOS UTC anchor is read without writing RTC data/alarm/status registers, with bounded update/stable-read checks, battery/calendar/BCD validation and explicit century-register policy. UTC is derived once from that anchor plus elapsed PIT monotonic time; normalized native/Linux realtime calls and console date share it. RTC failure returns unavailable, never fabricated epoch or uptime. Time adjustment, timezone/NTP, alarms and generic FADT century discovery remain absent. On the bf5faba56301 milestone, two bounded HPET windows calibrate an actual masked LAPIC countdown. A masked running firmware timer is explicitly adopted/stopped; LVT/divider configuration is restored, and the timer stays masked. PIT continues scheduling and IOAPIC redirection stays unchanged. On the 31e7e89ec239 milestone, PIT IRQ0 is explicitly routed through owned IOAPIC/LAPIC state with three actual ISR-observed interrupts and owner retention; PIC rollback is validated when adoption fails. PIT remains the time source. General APIC routing/clock-source policy, language TLS runtime/ELF TLS relocation, XSAVE/extended-state ownership and SMP remain separate work.

User page faults, invalid opcodes and other installed exception gates terminate the offending process and retain its exit/fault result. The native `nextd` supervisor demonstrates launch, IPC request/reply, wait/reap, child-fault survival, preemption/kill, stale handles and slot reuse, then remains alive. A bounded eight-service dependency/restart policy now validates cycles, instance identities, heartbeat deadlines, backoff and start budgets. PID1 applies this to one isolated worker, exercises forced exit/restart and heartbeat-stall recovery, and keeps the final worker alive with scoped log/channel capabilities. Console kill cannot control that supervisor-owned instance. Configuration now comes from config/services.bin inside the exact running nextd signed application bundle, with package/executable digest binding. PID1-only retrieval validates the complete output before copying. Eight bounded declarations carry exact worker package/digest, authority ceilings, dependency edges and restart/window/backoff/health policy; signed active-mask selection constrains admission. The default keeps one worker active to preserve two console slots. A separately signed alternate configuration starts two real concurrent workers: primary readiness precedes dependent spawn; primary failure stops dependent before recovery; both final workers stay alive. Worker launch checks exact independently authenticated identity and attenuates capability rights to 0x1b with no launcher or permission grants. This is not a general declarative service/session manager: per-service memory/CPU/I/O budgets, general service owners, health endpoints, persistent configuration and complete system transitions remain absent.

## Storage and durability

The VM uses a polling legacy virtio-blk driver with bounded queues, owned DMA buffers, 512-byte sectors and explicit write/flush operations. Read-only feature enforcement and unsupported flush errors are checked. Modern virtio, NVMe/AHCI, storage interrupts, IOMMU protection, hotplug and physical controller certification are absent.

The first 64 MiB of the development image remains a FAT32 boot volume at LBA 0, read through the short-name FAT reader. A separate trailing 1 MiB development extent contains the bounded COW store outside that entire volume. This layout has no GPT discovery or installation semantics.

The COW store supports eight files of at most 4 KiB, whole-file replacement, atomic rename/delete, generation-numbered commit superblocks, metadata/content CRCs, explicit data/root/commit flush barriers, and read-only fallback to a complete older snapshot. Any transaction I/O failure blocks further writes until remount. Mount does not repair or format unknown data. Kernel initialization formats only the deliberately blank generated development extent. See [FS-FORMAT.md](FS-FORMAT.md) for exact bytes, ordering and limits.

A nonblocking mutation guard serializes mounted-store mutations and reports reentrancy without spinning. Host race tests exercise concurrent directory snapshots, rename, unlink and stale identities; they do not establish guest SMP behavior. Host crash tests cover every transaction write/flush boundary, torn writes, namespace operations, failed flushes, media errors, full tables, corruption and protected extents. A separate integration test writes a file, shuts down the first VM, reads it in a fresh VM using the same scratch disk, and removes it; both boots preserve the protected FAT32 bytes and the source image. Clean reboot persistence and modeled crash consistency do not establish arbitrary power-loss behavior on physical hardware. The native adapter exposes open/read/write/seek/stat under launcher-controlled `/native/`. Current source uses up to eight open descriptions and shared inode content: independent opens have separate offsets; duplicates and IPC transfers retain one description and share its offset. A linked write commits a bounded COW replacement before changing shared cached content. Console replacement, rename and remove update the same inode state after backend success. Unlink or destination replacement detaches the old open inode from its name; existing handles retain its content, and subsequent detached writes remain in memory until final close. A new open of the reused name gets distinct identity. The f42210 positive VM scenario exercises independent/shared offsets, rename replacement, unlink lifetime and recreated-name isolation; milestone 418ea records the earlier exclusive-open behavior. This remains a bounded development store without mounted VFS namespaces, links, credentials, asynchronous I/O or full POSIX/NT semantics. A bounded Linux descriptor adapter now provides read/write/open/close/fstat/lseek/dup/openat plus positional `pread64`/`pwrite64` under explicit console launch authority in `/native/`; eight descriptors preserve shared stream identity and access rights. The original file fixture exercises shared open descriptions and positional I/O in the guest. A host-only read-only COW verifier checks the exact development format and reports candidates/corruption without repair, hashing its source to detect changes. An additional host recovery tool opens an offline scratch image read-only, exports a selected verified committed generation to a fresh output directory, and checks the exported snapshot without repairing source media. Persistence validates it against actual guest-written files while preserving every source byte. This covers bounded format recovery, not authenticated backups, full fsck, encryption or physical power-loss certification. A separate host GPT planner/inspector encodes/validates standard CRC-protected headers/entries and emits a dry-run layout; it never installs or writes a target. The read-only verifier also checks the actual journal left by the two-boot persistence VM and confirms durable removal; the GPT tool has host proof and no guest discovery/installer integration. A bounded host recovery exporter can copy only a fully verified committed generation to a new private destination, using source/file hashes and a completion marker; it never repairs source media or overwrites existing output. Host tests cover corruption, symlink/special-file rejection, publication interruptions and an actual exporter process exit. The sixth-wave persistence source now exports and verifies the real guest scratch snapshot before deleting it, comparing generation/files/hash with the independent verifier; this new recovery VM gate remains pending a fresh run. Full NextFS, user snapshots, quotas, encryption and general fsck repair/salvage remain outstanding.

## Network, input and Prism

The legacy virtio-net driver acquires a DHCPv4 lease through bounded DISCOVER/OFFER/REQUEST/ACK exchanges, validates address/mask/gateway/DNS/server and lease timers, and sends ARP, ICMP echo and an IPv4 UDP echo datagram on the QEMU profile. The host echo response validates actual bidirectional UDP traffic. UDP decoding checks lengths, addresses/ports and checksums; IP options and fragments are rejected. The production DHCP runtime also has deterministic host tests for lease renewal, rebinding, expiry and restart; the guest still demonstrates acquisition only, with no installed renewal/rebinding service. A bounded TCP client now performs a real handshake, HTTP request/response and close against a loopback host peer through QEMU, with checksums, sequence/window validation and bounded retransmission. This is one transport probe, not a socket API, browser, general HTTP client or complete TCP interoperability certification. A bounded DNS resolver now exchanges actual UDP A/AAAA questions with a synthetic loopback-host zone, retries one deliberately dropped request, validates framed replies and observes two-second TTL cache hits, monotonic expiry and a wire refresh. This is a local development peer, not use of the DHCP-advertised DNS server or general Internet resolution. Host tests cover negative caching and malformed inputs; an AAAA answer does not provide IPv6 transport. Native connected UDP socket capabilities now exchange actual nonce/empty datagrams through a retained virtio owner to a fixed local development peer. Signed NETWORK requests and independently attenuated grants are checked on creation/duplication/transfer/use, including a refused recipient import. Eight global sockets have bounded queues, generation/refcount lifetimes, copyout-before-consumption and level readable waits. Permanent driver staging buffers retain DMA ownership independently of socket teardown. This is not a general socket service: POSIX/Winsock APIs, arbitrary peers/listeners/routing, a userspace netd, IPv6, TLS, firewall policy, Wi-Fi and physical network certification remain absent. See [UDP profile](UDP-PROFILE.md).

PS/2 keyboard and auxiliary mouse input are polled. Prism renders into a bounded software back buffer, then copies the completed visible rows into the same-format front framebuffer. Geometry and front-buffer bounds are checked before writes, stride padding is preserved, and a frame-generation marker identifies completed presentation. The buffer holds at most 1920 × 1080 stride pixels; this is a fixed memory limit, not GPU acceleration or a vblank/tear-free guarantee. VM screenshots synchronize with completed frames rather than racing an in-progress render. The development latency runner measures actual QMP PS/2 focus and typed-command actions until a strictly subsequent completed software-frame marker, first with baseline tasks and then with two noncooperative children. Its host wall-clock results include TCG, host scheduling and instrumentation; they do not measure kernel IRQ latency or physical/vblank presentation. See the [reference measurements](LATENCY-REFERENCE.md).

Terminal, Files, System Monitor, persistent appearance Settings, Editor and Calculator share the development desktop. Files displays supplied verified metadata/content previews; Monitor uses supplied process/clock data. Focus, move, resize, minimize, maximize, restore and close operations use bounded window state. Mouse events control pointer and focus/drag behavior. Settings persists bounded theme, accent and text-scale choices. Text scaling applies to the Settings surface only; it does not provide global desktop/application scaling, and the broader system settings catalog remains incomplete. See the [guest screenshot gallery](PRISM-VISUAL-GALLERY.md).

Console-owned process output reaches Terminal through an eight-record queue with UTF-8-safe 512-byte chunks and explicit overflow reporting. It does not supply a PTY, pipes or job control. Editor loads bounded UTF-8 documents, edits through PS/2 input and saves via COW. It compares the current content/existence with its load baseline before saving; external changes report a conflict while preserving unsaved text. It provides no general concurrent merge, rich formatting or user-isolated app process. All these panels/rendering currently live in the kernel address space. Home search matches the supplied installed-panel labels and actual authorized local file metadata; selecting a file loads authoritative content in Editor. It is bounded local matching without a persistent index, settings/content search, searchd or permission-location configuration. A trusted kernel-hosted modal file chooser now binds requests to signed process identity/lifetime, displays package/access and returns a read-only or read/write file capability only after trusted selection. Approval holds the existing inode before consuming the move-only grant, preventing later name reuse from redirecting authority. Denial, deadline, cancellation, stale/replayed requests and cleanup are bounded; host adapter tests cover inode retention and process teardown. The positive guest uses real PS/2 consent, denies writes on a read-only grant, rejects via UI and checks unattended expiry/cancellation. This is session-local existing-file consent in /native/, not persistent permission policy, arbitrary namespace access, save/create dialogs or a userspace broker. The bounded native copied-pixel surface/input contract below does not provide an isolated userspace compositor, general display server, GPU modesetting/acceleration, complete font shaping, general clipboard/portal system, assistive technology or finished system application suite.

The AC97 development driver owns its DMA descriptors and PCM buffers, configures 48 kHz signed 16-bit stereo output, and plays a bounded 250 ms, 1 kHz triangle-wave probe. The VM test checks DMA completion and captures the QEMU output as WAV, verifying matching stereo channels and the expected period. This is a real device-output path on the named VM profile. It is not microphone capture, an audio service, stream mixing, persistent volume settings, a latency guarantee or physical audio certification. Modern audio controllers, `audiod`, application streams, capture permissions and device routing remain outstanding.

## Explicit Linux personality

Only explicit `/compat/linux/` executable paths select the Linux development profile. It has a separate dispatcher and rejects entry through the native gate. Native processes cannot silently select Linux syscall semantics from numeric collisions.

The profile accepts fixed ET_EXEC x86-64 ELF within the same bounded image window, containing only supported PT_LOAD records. It initializes a minimal Linux-style stack and implements `write` to stdout/stderr, `getpid`, `sched_yield`, `exit`, `exit_group`, bounded `brk`/anonymous `mmap`/`munmap`, monotonic `clock_gettime` and `nanosleep`, plus bounded `openat`/`read`/`write`/`close`/`fstat`/`lseek`/`dup` and positional `pread64`/`pwrite64`, `getdents64`, `getcwd` and `chdir`; unsupported calls return Linux ENOSYS and invalid descriptors/pointers return EBADF/EFAULT. Working-directory and relative open/openat resolution are process-owned and confined to the explicitly granted `/native` namespace. Retained directory-origin identity is checked before relative lookup; removed/renamed/recreated origins fail instead of retargeting a replacement name. This bounded symlinkless profile does not implement general POSIX cwd/rename or mount semantics. A bounded read or write may be partial. PT_INTERP, PT_DYNAMIC and other unsupported runtime requirements are rejected.

The identical original static `hello.elf` runs directly on host Linux and within Helix, exercises selected Linux syscall/error semantics, prints its success marker and exits 37. A separate gate fixture checks personality isolation; original memory, clock and file fixtures exercise mapping bounds/W^X, heap changes, monotonic time, descriptor state, and positional I/O. The bounded file fixture exits 46 in the `cpu=max` QEMU smoke image. Anonymous mappings support only the documented private-anonymous profile, and sleeping uses the single-CPU scheduler rather than a POSIX signal/restart implementation. This is one precisely scoped compatibility scenario, not general unmodified Linux application support. Dynamic linking, libc/language TLS, signals, general file namespaces/full POSIX concurrency, sockets, VDSO/proc/sys namespaces and a public application support catalog remain unimplemented. No Linux kernel code runs in the guest. An explicit `/compat/nt/` PE32+ AMD64 profile executes an original fixture through three Win64 API shims: GetStdHandle, WriteFile and ExitProcess. A second fixture validates invalid handles/pointers and cross-personality gate rejection. This is Helix-only evidence for a bounded fixed-image console profile, not an actual Windows-certified binary or general NTDLL/Win32 compatibility. See [NT profile](NT-PROFILE.md) and [Linux profile](LINUX-PROFILE.md).

The kernel UART adapter uses a bounded transmit FIFO and bounded hardware-drain attempts, retaining queued bytes across stalls and reporting accepted/transmitted/dropped/absent counters. Both recorded CPU profiles observed stalls and zero rejected/absent bytes. Queue exhaustion is observable and can reject output; this is not an unlimited or universally lossless serial guarantee.

## Evidence and release boundaries

| Scope | Evidence establishes | Remaining limit |
| --- | --- | --- |
| `host_tested` | Named bounded primitives satisfy their host tests | Does not establish guest integration or hardware operation |
| `boot_smoke` | A recorded image reaches named QEMU/OVMF milestones | Does not establish arbitrary PC support or product readiness |
| `integrated` | A documented guest scenario works end to end | Requires separate physical-profile certification |
| `certified_hardware` | A scenario works on identified physical devices/firmware | Does not generalize to other hardware |

Source12 adds an uninvoked `stage_private_root` hardware prerequisite and a
transactional real-table builder. It allocates only on request from an
exclusively borrowed, final-map-validated physical allocator, checks each page's
unchanged BSP RW/NX identity mapping before dereferencing it, and constructs a
new PML4/PDPT/PD/PT tree without borrowing any BSP subtree. At most 32 table
pages and 8192 mapped leaves are allowed. Allocation and write errors roll back
unpublished ownership; an independent complete walk rejects unknown pages,
cycles, duplicate subtrees, extra/missing leaves, foreign physical aliases,
user/global/huge/reserved flags and writable executable mappings. Table pages
receive their own RO/NX identity leaves. Once audited, `PageAllocator::retain`
permanently excludes those allocations from `free` and future reuse, including
after timeout quarantine. Retained root metadata exists without any default
physical allocation or activation.

The staged AP root includes supervisor RX low code, RW/NX low emergency stack,
RO/NX bootstrap descriptor metadata, linker-owned kernel RX text and RO/NX
rodata, only its own guarded 64KiB high stack and page-aligned RW/NX mailbox,
its private RO/NX IDT, the two RO/NX A20 witness pages, and the validated RO/NX
uncached HPET page. BSP stacks, other AP stacks/mailboxes and other writable
kernel data are absent. Mailboxes now occupy independent 4KiB pages, preventing
a writable leaf from granting access to a neighboring CPU mailbox. Bootstrap
bytes are reconstructed from exact handler symbols and compared in full before
root staging; a retained root prevents later low-record restaging.

The current handoff reserves one low emergency-stack page. Sixteen byte-sized
slots in that page cannot become sixteen independently protected paging leaves.
The hardware adapter therefore accepts only a single staged AP in slot0 with
all other records inactive. It neither publishes CR3 into the mailbox nor
switches a CPU/root, maps BSP code executable, or sends INIT/SIPI. Extending
hardware staging to more APs requires separate page-owned low stacks. The pure
builder can create disjoint roots already, but that is not a many-CPU activation
claim. CR0/LMA transition NMI coverage remains the activation blocker.
